  Reading:
    The pool is not magic: it trades dynamic allocation for an index
    into a pre-allocated array, and the per-lcore cache avoids even the
    atomic operation on the shared ring -- which is what the NO-cache row measures.

    The direction of the two batch columns is the main result: asking for
    more objects at once makes each object CHEAPER in the mempool and MORE
    EXPENSIVE in malloc. The reason on the malloc side lies inside glibc's
    allocator and this project does not investigate it; what matters here is
    that the batching strategy, central to the data plane, only pays off on
    one of the sides.

    None of these numbers includes page faults: the pool is already warm.
    In production, the first pass over the memory is more expensive.
