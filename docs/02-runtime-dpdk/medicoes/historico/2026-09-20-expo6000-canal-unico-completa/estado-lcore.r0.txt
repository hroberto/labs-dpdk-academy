  Two columns that are often confused:

  * "real CPU(s)" comes from rte_lcore_cpuset(): it is where the lcore's
    thread is actually pinned. With -l 0-3 it matches the lcore number; with
    --lcores '0@6' lcore 0 starts running on CPU 6.

  * "index in node" comes from rte_lcore_to_cpu_id(), whose name MISLEADS: the
    documentation says "the id of the lcore on a socket starting from
    zero", that is, an index relative to the NUMA node -- not the CPU
    number. Using it to pin a thread or pick an IRQ puts the work on the
    wrong core, and the symptom shows up only in performance.

== State machine of the worker lcore ==

  This DPDK version exposes TWO states: WAIT and RUNNING.
  Until DPDK 20.11 there was a third, FINISHED, still described in
  most of the material available on the web.

  apos rte_eal_init:     lcore 1: WAIT     lcore 2: WAIT     lcore 3: WAIT    
  apos remote_launch:    lcore 1: RUNNING  lcore 2: RUNNING  lcore 3: RUNNING 
  durante o trabalho:    lcore 1: RUNNING  lcore 2: RUNNING  lcore 3: RUNNING 

  values returned by the workers:
    lcore 1 -> 107
    lcore 2 -> 207
    lcore 3 -> 307

  apos wait_lcore:       lcore 1: WAIT     lcore 2: WAIT     lcore 3: WAIT    

  Note that the state returns to WAIT on its own: there is no FINISHED to
  observe. rte_eal_wait_lcore() is what delivers the return value,
  and that is why it remains mandatory even when the worker
  has already finished.
